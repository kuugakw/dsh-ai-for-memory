# 剩余风险与已接受的边界

这份文档记录**已知但未完全消除**的风险，避免把“做了缓解”写成“已经解决”。评审时如果这些前提变了，需要重新评估，而不是沿用旧结论。

## 1. 推理引擎仍在同一 OS 账户下

**现状**：`llama-server` 是插件 spawn 的子进程，但插件不做张量推理；进程只绑定 `127.0.0.1`，`extraArgs` 有白名单。它不是容器、不是独立用户、也没有 seccomp/Job Object 之类的沙箱。

**残余风险**：恶意 GGUF 或 llama.cpp 自身漏洞可以在同一用户权限下读记忆目录和其他文件；token 泄露也能读。插件能做的只是不把引擎暴露到网络、不让模型配置改绑定/权重路径。

**为什么没做**：跨平台进程沙箱（Windows Job Object、Linux namespaces、macOS sandbox）会改变安装与兼容成本；当前威胁模型是“本机同一用户可信”，不是多租户隔离。需要更强隔离时应把引擎放到独立账户/容器里。

## 2. SQL 白名单是唯一闸门

**现状**：`isSafeSelect()` 是 SQL 通道唯一的静态闸门：拒绝 `sqlite_master`/`pragma`/写语句/自连接/`ATTACH`/扩展函数，只允许 `knowledge_docs`、JSON 表函数和 CTE。对抗用例覆盖了已知逃逸。

**已评估但否决**：SQLite `authorizer` 回调曾作为第二道闸门评估，因覆盖范围/兼容性/维护成本被否决；当前选择是“单闸门 + 解析层测试 + 只读内存库”，而不是两个半吊子判断。

**残余风险**：白名单解析器本身的漏洞就是唯一失败点；SQLite 版本升级引入新函数时需要补白名单/测试。改动 `isSafeSelect` 必须同时更新对抗用例，不能只加允许项。

## 3. 脱敏是启发式，不是数据丢失防护

**现状**：`redactSecrets()` 用正则匹配已知前缀（`ghp_`、`sk-`、JWT、私钥、`Authorization`、`password=` 等），在写入边界和深层 JSON 上执行；迁移会回填旧数据。

**拦不住的**：

- 散文里拆开的密钥（`ghp_` 和后半段分开写）；
- 没有已知前缀的 base64 blob / 高熵字符串；
- 同形字符（Cyrillic/Greek lookalike）拼出的关键字；
- 用户自己把 `redactSecrets: false` 打开，或把密钥写进图片/附件；
- 迁移备份保存的是**脱敏前**原文（`backups/schema-v1-*`），敏感级别高于当前语料。

**结论**：脱敏降低“密钥被顺手写进长期语料”的概率，不承诺“任何形态的密钥都不会落盘”。真正的边界是不要把密钥粘进对话；备份要按敏感数据管理。

## 4. 规模只验证到 3k 可用

**现状**：3k / 10k / 30k 曲线见 [规模压测](benchmarks.md)。3k 冷启动约 3.1 s，10k 约 5.7 s，30k 约 18.6 s；30k 的 hybrid 首次约 19.4 s、SQL 分类统计约 22.3 s，出现非线性悬崖，第二次 hybrid 又回到 0.1 ms。

**结论**：3k 是当前可接受规模；10k 冷启动已明显；**30k 还不能算支持**，hybrid/SQL 需要单独 profiling 和优化。面板首次打开 10k 库会有数秒等待，这是已知体验成本。

## 5. 发布 tag 仍未签名

**现状**：npm 0.5.25 有 provenance/OIDC trusted publisher；GitHub tag 是 annotated 但未 GPG/SSH 签名。验证脚本会明确报告 `signed tag: false`。

**残余风险**：能识别“是否由本仓库 workflow 发布”，但不能用 `git verify-tag` 证明 tag 是维护者签的；详见 [发布验证](release-verification.md)。

## 变更规则

新增功能如果触及以上任一边界（引擎参数、SQL 白名单、脱敏规则、规模目标、发布流程），需要在本文件更新“现状/残余风险/为什么没做”，并在对应测试里加一条失败用例；不要只在 CHANGELOG 写“加固”。
