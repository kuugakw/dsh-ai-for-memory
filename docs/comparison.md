# 记得住，也要管得住：主流 AI 记忆插件对比与 AI for Memory 的定位

> 大多数记忆插件解决的是「记住」：把对话里的事实抽出来，下次再召回。AI for Memory 多做了四件工程上的事——**上下文、检索、数据库、审查**。下面按这四块展开：先讲本插件怎么做，再讲主流方案通常怎么做，最后讲这个差异换来什么。

## 0. 一句话对照

| 能力 | 主流方案常见做法 | AI for Memory |
|---|---|---|
| **上下文** | 不碰窗口；或压缩后不可逆 | 清理前先完整存档，可恢复；任务进行中硬重置并续接 |
| **检索** | 单通道向量召回 | SQL / BM25 / RAG 三通道，按问题自动选路，可融合 |
| **数据库** | 向量库/图库是唯一真相 | JSON 是底座，SQL 与 RAG 只是派生视图 |
| **审查** | 写入即事实 | 冲突先确认、模型自述降权、高风险决策先正反合 |

## 1. 上下文：清得掉，还能接得上

本插件把「上下文」当成要管理的资源，而不是一次性丢弃的聊天记录：

- 每轮对话有独立的记忆目录；上下文清理 = **先完整存档，再腾出窗口**，`aim_context restore` 按 `restoreMaxChars` 预算从尾部注入，不是整份倾倒；
- 上下文占用到阈值（默认 70%）时，在任务**进行中**做硬重置：清出当前轮较早的工具步骤（保留当前请求、最近 3 步和最近几轮），注入「当前请求 + 最近进展 + 相关记忆」的续接包，**继续同一个任务**；
- 每 N 轮（默认 5 轮）的自动整理按话题相似度选择，低相似度的老轮次先存档再清出，高相似度保留；
- 对话级权限：不开放 / 只对指定对话开放（`viewers` 名单，可多选）/ 对全部对话开放；不开放的对话不出现在检索、恢复和面板视图里。

主流方案通常不碰上下文窗口（Anthropic KG Memory、Basic Memory 只管记），或者像 Claude-Mem 那样压缩后注入、但压缩不可逆；少数做「清空后重新注入」的，也没有「按预算恢复 + 任务中续接」这层。

换来的是：长任务不会因为清上下文丢掉线索；窗口压力可控；客户 A 和客户 B 的对话可以真正互不可见。

## 2. 检索：三条通道，按问题自动选路

- **SQL 通道**：指标、聚合、精确 `doc_id` 类问题走 Text-to-SQL（基于 JSON 底座的只读内存表）；
- **BM25 通道**：模糊、开放性的文档问题走本地 BM25；
- **RAG 通道**：面板「RAG 挂载」开启且索引就绪时，语义结果与 BM25 结果用 RRF 融合；RAG 未挂载就只用 BM25；
- **自动路由**：`auto` 判断问题类型，SQL 翻不了就回退向量，向量零命中就反向用 SQL 兜底；
- 排序叠加**本对话的最近使用权重**（14 天半衰期，只影响本对话，不污染其他对话）；同一事实在多个对话各存一份时，合并折叠成一条「另见」；
- 模型自述（`provenance=model`、未确认）默认降权并标黄，不当作项目事实。

主流方案基本是单通道：mem0、mcp-memory-service 靠向量召回，Basic Memory 靠全文 + 图遍历，Anthropic KG Memory 靠图查询。没有「按问题选通道」，也没有「对话级使用权重」和「跨对话折叠」。

换来的是：「这周记了几条错误修复」这种统计问题不必猜；语义问题走向量；精确 id 走 SQL；召回质量不够时知道是缺索引还是缺查询改写。

## 3. 数据库：JSON 是底座，SQL 和 RAG 只是视图

- 每个对话一个目录：过程记录、归档、快照、知识库、决策、上下文、冲突审计、面板审计都在里面，**JSON 可读、可 diff、可 git**；
- SQLite 是**派生镜像**：从 JSON 建内存只读表，磁盘上的某一行坏掉不会把视图带崩；需要文件时用 `export types=sql` 导出 `knowledge.sqlite`；
- RAG 索引也是派生：建在知识库上，可随时挂载/摘除，索引文件损坏删掉重建即可，不影响 JSON 底座；
- 导出：知识库 JSON / Markdown、SQLite、RAG 索引，可指定目标目录；
- 数据层能自检：`aim_repair action=doctor` 并查会话日志、`workspace.json` 索引、投影缓存三处，报告序号断层、缺日志、投影比日志新，按 `ghosts=auto` 写占位日志或清索引条目。

主流方案把向量库或图库当唯一真相（mem0、Graphiti、mcp-memory-service），用户只能看到召回结果，看不到「为什么记了这条」。

换来的是：可审计（每个字节都能打开）、可迁移（换机器不锁死）、坏了能修（不是只能重建索引）。

## 4. 审查：高风险先正反合，不可逆直接拒绝

- `aim_decide` 对不可逆或高风险操作做正反合审查：`irreversible=true` 直接拒绝；`irreversible=false` 必须同时给出 `recoverable_via` 才放行；缺字段返回 `needs_more_info`。高风险不再按理由字数放行，只看操作是否可逆；
- 每轮工具调用与本地文件改动自动记一条「常规」决策；`aim_decide` 的审查记录在「风险」；面板与 `aim_memory status` 分开计数；
- 知识写入有冲突闸门：新知识与已有知识相近但不同时返回 `needs_confirm`，先问用户，`confirm=true` 才覆盖，旧正文留在 `changes` 审计里；
- 事故（文件损坏、数据丢失、严重误操作）单独记为 `incidents` 类型，不混进普通知识；
- 面板有操作审计：批量开放/关闭对话、面板操作都会留记录。

主流方案写入即事实：KG Memory 和 mem0 都不做冲突确认，也没有「决策复审」和「风险分级」。

换来的是：模型写的东西不会被当成项目事实；覆盖有据可查；高风险操作留痕，事后能复盘为什么当时放行了。

| 方案 | 形态 | 存储 | 上下文治理 | 审查 |

## 6. 优点与局限

优点：

- **可审计**：四层数据都是 JSON，出问题能定位到文件；
- **可迁移**：JSON 底座 + 导出格式，不锁死；
- **不丢上下文**：清出可还原，任务中硬重置还能接着跑；
- **检索按需选路**：统计、精确、语义各走各的通道；
- **权限粒度细**：能精确到「A 只对 B、C 开放」；
- **零外部依赖**：本地规则即可工作，外部模型失败自动回退。

局限：

- **绑定 DSH**：面板、tokenMeter、日志修复是 DSH 专属；MCP 出口能桥接其他客户端，但不是一等公民；
- **单机单用户**：没有多租户、团队共享、云同步；
- **无时序图推理**：不追踪「事实如何演化」，只有时间戳和变更审计；
- **语义召回依赖外部模型**：默认哈希向量 + BM25，RAG 需要自己配 Embedding/Rerank；
- **生态小**：没有跨客户端插件市场。

一句话：别的方案在比「记得多」，这个插件在比「记得住、查得到、清得掉还能恢复，并且知道该给谁看」。
