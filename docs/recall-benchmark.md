# 记忆召回基准

规模压测只回答「多快」，这个基准回答「找不找得到」。数据集在 `scripts/recall-dataset.mjs`：41 条项目记忆、20 条查询，每条查询有一个已验证目标；部分主题带近似干扰项、未确认模型说法，或复述查询词但答案相反的陷阱。

```bash
node scripts/bench-recall.mjs
node scripts/bench-recall.mjs --json --topk=10
npm run bench:recall
```

指标：Recall@1/3/5、MRR、nDCG@10；另外统计「未确认模型说法进入 top-3」的比例。查询分四类：

- `exact`：关键词与目标高度重合；
- `paraphrase`：换一种说法，关键词重合少；
- `trap`：干扰项复述查询词但给出相反答案（例如「可以绑定 0.0.0.0 吗」）；
- `provenance`：同时存在未确认的近似模型说法，看排序是否把它压下去。

## 最近一次结果

Node 26、Windows；纯本地零依赖路径（BM25 + 128 维哈希向量 + RRF），未接真实 Embedding。

| 模式 | R@1 | R@3 | R@5 | MRR | nDCG@10 | 平均耗时 |
|---|---:|---:|---:|---:|---:|---:|
| BM25 | 65.0% | 85.0% | 90.0% | 0.766 | 0.811 | 0.43 ms |
| vector | 40.0% | 85.0% | 85.0% | 0.614 | 0.698 | 0.26 ms |
| hybrid | **65.0%** | **90.0%** | **95.0%** | **0.771** | **0.816** | 0.16 ms |

按 hybrid 分类：

| 类型 | R@1 | R@3 | R@5 | MRR |
|---|---:|---:|---:|---:|
| exact | 100% | 100% | 100% | 1.000 |
| paraphrase | 50.0% | 83.3% | 100% | 0.653 |
| trap | 0% | 100% | 100% | 0.500 |
| provenance | 66.7% | 66.7% | 66.7% | 0.667 |

未确认模型说法进入 top-3：**0%**（hybrid，provenance 查询）。

## 怎么读

- **hybrid 在 R@5 上最好（95%）**，说明 RRF 融合对“关键词能对上、但单路排序不稳”的查询有用；vector 单独用明显更弱，因为它不是语义模型，只是按 token 哈希的余弦。
- **paraphrase R@1 只有 50%**：查询「旧值被替换前会不会先问我」和目标「冲突时先询问用户，确认后才覆盖旧值」共享的词很少；哈希向量只能覆盖共享 token，不能补同义改写。要提升这部分需要真实 Embedding 模型，这是基准刻意保留的“零依赖基线”。
- **trap R@1 为 0%**：目标与干扰项都复述了查询词，检索器无法仅凭文本判断哪句是真的（「可以绑定 0.0.0.0 吗」的目标说不能，干扰项说可以）。这不是排序 bug，而是检索的边界：答案真伪要靠 provenance/冲突闸门/引用核对，不能靠 top-1。
- **provenance 查询未确认说法 0% 进 top-3**：未确认惩罚有效；`q-engine-prov` 仍然 miss（查询用「监听」，目标写「绑定」，没有共享 token），说明 token gate 会漏掉无字面重叠的查询。
- **trap 的 R@1 低但 R@3 100%**：目标总在候选里，只是排在错误答案之后；面板把来源和证据展示出来，正是为了让用户能看出这一点。

## 什么时候更新

改动分词、RRF 权重、未确认惩罚、RRF_K 或引入真实向量后，先跑本基准，把新表覆盖到本页；不要只跑规模压测。
