# AI for Memory 的特点与优点

> 一个面向 DSH 的项目级记忆插件：**记得住、查得到、清得掉还能恢复**，数据坏了能修，写进来的东西还知道该给谁看。

## 1. 定位：项目记忆，不是聊天收藏夹

它关注的是项目工作流里的事实、约定、错误修复、决策和上下文，而不是「用户喜欢什么」或「聊天记录备份」。

- **六层结构**：过程记录（staging）、分类归档（archive）、快照（snapshots）、知识库（knowledge）、决策（decisions）、上下文（contexts）——每层各管一件事，写进来之后还会被归档、提炼、审查；
- **一条一句的知识**：知识库里的每条结论都带分类和出处，可检索、可提炼、可导出；
- **本地优先**：JSON 是底座，没有 API Key 也能用，所有记忆默认保存在本地。

## 2. 上下文：清得掉，还能接得上（强项）

插件把上下文当作要管理的资源，而不是一次性丢弃的聊天记录。

- **清理 = 先存档再腾窗口**：上下文整理前先完整存档，之后随时 `aim_context restore` 按预算调回，不是整份倾倒；
- **任务进行中也能续**：占用到阈值（默认 70%）时，在任务进行中做硬重置——清出当前轮较早的工具步骤，注入「当前请求 + 最近进展 + 相关记忆」的续接包，**继续同一个任务**；
- **按话题整理**：每 N 轮（默认 5 轮）按话题相似度选择，低相似度轮次先存档再清出，相关轮次保留；
- **对话级权限**：每个对话独立目录，默认私有；可以只对指定对话开放（可多选），也可以对全部开放；不开放的对话不出现在检索、恢复和面板里。

带来的好处：长任务中途清上下文不丢线索；窗口压力可控；客户 A 与客户 B 的对话可以真正互不可见。

## 3. 错误恢复：坏了能修，坏过能查（强项）

其他记忆插件大多在追求「不写错」，它多准备了一套「写错了、坏了怎么办」。

- **会话日志修复**：`aim_repair` 提供 scan（快速头部扫描）、deep（解压逐事件校验）、repair（先备份原文件；优先把插件写坏的游离 developer 便条改写成等价的 user 便条、保留全部历史，否则截断到第一处损坏并用合成收尾事件补全回合）、compact（结构有效但物理膨胀时重排 zstd 帧，事件一个不改）；
- **三处对账**：`aim_repair doctor` 并查会话日志、`workspace.json` 索引、投影缓存，报序号断层、缺日志、投影比日志新、回合没写成收尾；修复时按策略截断、归档过期投影、给缺日志的会话写占位或清索引条目；
- **删除有备份**：清理索引前先备份 `index.jsonl`；修日志前先备份原文件；任意状态可保存为快照并 `restore` 回滚；
- **写入有兜底**：用户数据写入 fsync，hook 失败不阻断本轮；
- **错误可复用**：修过的错误可以从过程记录提炼成 `errors_fixes` 知识，下次检索得到；事故单独记为 `incidents`（发生了什么 / 影响 / 根因 / 修复 / 预防）；
- **覆盖有审计**：知识冲突先确认再覆盖，旧正文保留在 `changes` 里；冲突记录进 `conflicts.jsonl`。

带来的好处：DSH 打不开的会话、对不上的索引、写坏的日志，在这里有确定的修法；修之前先备份，修完能验证。

## 4. 检索：三条通道，按问题自动选路

- **SQL 通道**：指标、聚合、精确 `doc_id` 类问题走 Text-to-SQL；
- **BM25 通道**：模糊、开放性的文档问题走本地 BM25；
- **RAG 通道**：索引就绪时语义结果与 BM25 用 RRF 融合；未挂载就只用 BM25；
- **自动路由**：SQL 翻不了回退向量，向量零命中反向用 SQL 兜底；
- **对话级排序**：本对话最近使用过的条目加权（14 天半衰期，不污染其他对话）；
- **跨对话折叠**：同一事实在多个对话各存一份时合并成一条「另见」；
- **可信度分层**：模型自述默认降权标黄，不当作项目事实。

带来的好处：统计问题不必猜，语义问题走向量，精确 id 走 SQL；召回质量不够时知道是缺索引还是缺查询改写。

## 5. 数据库：JSON 是底座，SQL 和 RAG 只是视图

- 每个对话一个目录，过程记录、归档、快照、知识、决策、上下文、冲突审计、面板审计都在里面，**JSON 可读、可 diff、可 git**；
- SQLite 是**派生镜像**（内存只读表），某一行坏掉不会把视图带崩；需要文件时 `export types=sql`；
- RAG 索引也是派生：可挂载、可摘除，删掉重建不影响底座；
- 导出支持知识库 JSON / Markdown、SQLite、RAG 索引，可指定目标目录。

带来的好处：可审计（每个字节都能打开）、可迁移（换机器不锁死）、坏了能修（不是只能重建索引）。

## 6. 审查：高风险先正反合，不可逆直接拒绝

- `aim_decide` 做正反合审查：`irreversible=true` 直接拒绝；`irreversible=false` 必须给出 `recoverable_via` 才放行；缺字段返回 `needs_more_info`；高风险不按理由字数放行，只看操作是否可逆；
- 每轮工具调用与本地文件改动自动记一条「常规」决策，风险审查记「风险」，面板与状态里分开计数；
- 知识写入有冲突闸门：相近但不同的知识先问用户，确认后才覆盖，旧正文进 `changes` 审计；
- 事故单独归档为 `incidents`；面板批量操作也有审计记录。

带来的好处：模型写的东西不会被当成项目事实；覆盖有据可查；高风险操作留痕，事后能复盘为什么当时放行。

## 7. 工程上的好处

- **零外部依赖**：插件本体只用 Node 内置模块，装完即用；外部 Embedding/Rerank 是可选增强，失败自动回退本地规则；
- **面板随包**：总览、知识、上下文、诊断、审计都在 DSH 的 Web 面板里；上下文占用直接取自 tokenMeter；
- **自动但不扰民**：自动快照与自动整理默认开启，清出前一律先存档；不想要可以在面板切成手动；
- **数据在自己手里**：本地目录，可 git、可导出，换机器不锁死。

## 8. 适合谁

- 在 DSH 里长期做一个项目，需要「记得住 + 查得到 + 清得掉还能恢复」；
- 在意数据可读、可迁移、可审计，不想引入常驻服务；
- 需要对话之间的权限边界（比如客户 A 与客户 B 的对话不能互相读）；
- 被 DSH 会话日志损坏、索引对不上折腾过，想要一套能自检自修的数据层。

反过来，如果只需要跨会话的零散事实、或者想给多个 AI 客户端共用一份记忆，这个插件的六层结构和对话权限就偏重了。

## 9. 一句话

**别的插件在比「记得多」，它在比「记得住、查得到、清得掉还能恢复，并且知道该给谁看」。**
